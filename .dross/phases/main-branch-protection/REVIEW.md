## FLAG
- [test-contract] t-9's release guard refuses "a batch that would change ReleaseTag", but the plan never says what that tag is compared against. Since round 1, t-11 also sends ahead-and-behind bases to t-9, and an ordinary main-based `phase complete` hits phase.go:520 in exactly that state. At that point origin/main holds the phase's squash, which bumped the patch: phase execution bumps patch, and release.yml's header says "a phase ship bumps the patch … so it cuts a release". Local main, meanwhile, still holds ship's open chore commits or a pause snapshot. An implementation that compares the local tip's ReleaseTag with origin/main's sees v1.7.19 vs v1.7.20 and refuses a batch that never touched `[project].version`. Its scripted next step, "reset main to origin/main", would then throw away a chore that sits on no PR. The only guard contract is the purely-ahead positive case (1.7.19.1 → 1.8.0.0). t-13's pending-chore test passes on any refusal that doesn't mention --recover and moves no ref, so a release-guard refusal satisfies it as well. Neither test catches the false refusal.
  Suggestion: state the basis in t-9, either the change from merge-base to local tip, or the merged result's tag against origin/main's. Add a negative contract: an ahead-and-behind batch that leaves the version untouched while origin/main moved from 1.7.19.0 to 1.7.20.0 is published, not refused.
- [test-contract] t-14's description changes pushMilestoneHeadIfAhead unconditionally ("sends a .dross-only ahead set to the chore router and refuses code-ahead"). It has neither of the guard contracts t-11 has: no legacy/provider table for unprotected or non-GitHub bases, and no Unknown row. Today the function deliberately pushes code-ahead commits; that was the v1.5 close-out fix, milestone.go:997–1024. milestone_push_head_test.go pins this behaviour: TestMilestoneCompletePushesLocalCommitsBeforeOpeningPR (line 32) expects a committed late.txt on origin, and TestMilestonePushHeadCleanAheadPushesAndCounts (line 309) pushes two code commits. Even if the .dross-only half goes through t-11's router and inherits its probe, the code-ahead refusal as written applies on every provider. chore_push's "unknown → nothing is pushed" also covers a milestone base, and nothing in t-14 tests that.
  Suggestion: say in t-14 that the protection probe gates both changes. Protected routes to the chore router or refuses code-ahead; unprotected and non-GitHub keep today's push; Unknown refuses and names the reason. Add the same provider-table and Unknown rows t-11 carries.
- [test-contract] t-2 pins main's pull_request parameters but not the milestone ruleset's. The params contract ("required_approving_review_count != 0, strict is true, …") doesn't name the ruleset it covers, and only main's allowed_merge_methods is pinned. milestone/* receives three kinds of PR: phase PRs squash-merged (repo.squash_merge = true, ship.md §6 step 1), t-9's chore PRs merged as merge commits, and t-15's quick PRs. A milestone ruleset with allowed_merge_methods = ["merge"], or with any non-zero approval count (forbidden by the locked `approvals`), passes every t-2 contract and then blocks phase PRs. The first place this would surface is this phase's own ship into milestone/v1.7, right after t-16 applies the ruleset.
  Suggestion: run the approvals and merge-method assertions over both rulesets, and pin milestone's allowed_merge_methods to include both squash and merge.
- [test-contract] t-15 sends a standalone quick on a protected base to quick/<NEW_VERSION> and "opens a PR into the base", but never says how. No dross verb opens a PR for a non-phase branch: `dross ship` handles phase/<id> only (cli_tree.txt). So quick.md has to tell the agent to push quick/<ver> and run a raw `gh pr create`. That bypasses the OpenPR path and its screening. It also leaves three things open: who merges the PR, whether auto-merge is armed, and how the local base catches up afterwards. The quick-route contracts check only that quick.md mentions --check and quick/ and records no quick_base, so any wording, or none, passes.
  Suggestion: name the push, PR-open and merge commands in t-15's description, and pin them in the quick-route test the same way the push-ban test pins `git push origin <base>`.
- [test-contract] Two of t-12's contracts collide on provider "". The provider table requires every non-github value in ShipProviders, "" included, to print `not checked (<provider>)`. TestDoctorRunGolden must stay unchanged "with no [remote] configured", and its fixture is exactly that case: testdata/cli_surface/doctor_run.txt prints "project.toml has no [remote]", so provider is "". Read strictly, one of the two can't pass. Read leniently (print nothing), the "" row tests nothing. t-10's provider table has the same issue, giving `--check` → `not checked ()`. Separately, "with no origin/<main>, the section must name its workflow source" doesn't say what the fallback source is or what string names it.
  Suggestion: decide what "" (no remote) does, whether that's omitting the section or printing a named line plus a golden update, and write that into both provider tables. Name the no-origin/<main> fallback and its exact wording.
- [granularity] t-10 still touches 5 files and carries 12 contracts across three modes: preview, --apply and --check. It also owns the merge-commit warning, provider gating, the ProtectFixHint export and the README row. main.go, cli_tree.txt and README are registration plumbing, so the file count overstates the size, but the contract count doesn't. t-10 is also the sole wave-3 dependency of t-12 and t-15.
  Suggestion: consider splitting `--check` (read-only, RequiresPR-only, consumed by prompts) from preview/--apply.

One path that does this is milestone.md's "replace" arm. If local milestone/<v> already holds scope-time .dross commits, that push is now refused, and the error is git's raw pre-receive rejection, not a chore PR. It fails loudly and only on that edge case.

If so, ci.yml's push:main run and release.yml won't fire on Dependabot merges. That is harmless for releases, because bot merges never change the version and security bumps are released by hand under dependabot.yml's security_bump_release. It's worth adding to t-16's Dependabot follow-up so it is observed, not assumed.
