## BLOCKING
- [locked-decision] Two tasks contradict the text of `chore_push`, and neither change was written back to spec.toml. The lock says that on a protected base, `.dross` commits "reach origin as a `.dross`-only PR … never as a direct push."
  (a) t-11 (D5): when the protection probe returns Unknown, t-11 keeps today's `git push origin <base>`. On this repo the push is refused because the bypass list is empty. On any repo where the pusher holds a bypass, though, the push lands on a protected branch. doctor_reach scopes doctor to "any repo", and gh can be unauthenticated while git credentials still work. synthesis.md D5 says itself that the strict reading ("never attempt one") makes this a conflict.
  (b) t-9 (D3): t-9 refuses a main batch that changes ReleaseTag, so those commits never reach origin. The guard itself is right. The problem is that chore_push's `why` is now known to be false: "A .dross-only merge leaves [project].version unchanged". project.toml lives under `.dross/`, and release.yml tags any new projected version.
  plan.md's hard rule (line 301) says a task that contradicts a lock must be revised, or the decision unlocked in spec.toml with a why. Neither has happened, so verify will check the code against lock text that the code doesn't implement.
  Suggestion: amend `chore_push` in spec.toml so that its choice names both carve-outs (Unknown-probe fallback, release-tag refusal) and its why carries the corrected version premise. The alternative is to change t-11 to refuse without pushing on Unknown. Either way it is one decision; make it before execute.
