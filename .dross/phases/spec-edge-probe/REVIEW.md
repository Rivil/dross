## FLAG
- [locked-decision / test-contract] t-6 has `_spec.resume.md` say "replacing a spec clears [[edges]]", but §2b gets its open classes from `dross phase edges <id> --json`, which reads spec.toml on disk. The replace path only overwrites that file at §5 ("§5 overwrites the file only after the new spec is agreed"). So during a replace, §2b still sees the old spec's resolved classes and skips them. §5 then writes a spec with no [[edges]], and those classes are never proposed or recorded. Validate still passes, so nothing reports the loss. The t-6 contract only checks that the resume partial contains the "clears [[edges]]" wording. Nothing checks that the replace path treats all eight classes as open.
  Suggestion: in t-6's description and contract, state that on the replace path §2b ignores the on-disk edges and treats all eight classes as open. Then assert that instruction inside the §2b section or the expanded replace branch.

- [test-contract] t-1's contract "if omitempty is dropped, the legacy round-trip fails: a spec with no [[edges]] goes LoadSpec then Save byte-identical" can never fail. After LoadSpec of a legacy spec, `Spec.Edges` is nil. BurntSushi/toml v1.6.0 skips nil fields whether or not omitempty is set (encode.go:526 `if isNil(fieldVal) { /// Don't write anything for nil fields.`). If omitempty is removed, this test still passes. The phrase "byte-identical" also only holds for a fixture that is already in encoder-canonical form. A hand-written spec with comments or aligned `=` would fail for reasons unrelated to omitempty.
  Suggestion: test omitempty with a non-nil empty `Edges: []phase.Edge{}` and assert that the saved bytes contain no `edges` key. Separately, assert that a legacy spec round-trips with no `edges` key, rather than requiring byte-identity with a hand-authored file.

- [test-contract] t-2's contract "if minting ignores used ids … the printed id differs [from the seeded aaaaaaaaaaaaaaaa], and two consecutive calls print different ids" also can never fail. `deferred.NewID` reads 8 bytes from crypto/rand and has no seam. A mint that ignores the used set still returns a different id with probability 1−2⁻⁶⁴, and two random draws differ with the same probability. The named defect would go unnoticed, and Gremlins would record a survivor.
  Suggestion: either assert structurally that `new-id` goes through `mintDeferredID(root)`, which already applies the used set through `deferred.Collect`, and rely on mintDeferredID's existing tests. Or give t-2 a randomness seam so a forced collision with the seeded id proves the retry.

- [locked-decision scope] t-1 narrows `deferred_link` to "Deferred ids resolve against this spec's own [[deferred]] only", and t-3 pins that down ("the same id present only in another phase's spec fails"). The locked decision only says "validate checks it exists". The narrowing is defensible, but it is recorded nowhere as a decision. It also rules out a real case: an edge whose answer is "already parked elsewhere". This very spec's c-1 does exactly that with criterion `deferred = ["ddf9c9e63e17d0fc"]`, which lives in exec-taint-enumeration's spec. Under t-1, an edge in that situation has to re-file a duplicate [[deferred]] entry in the current spec, and board sync then mirrors the duplicate as a second someday card.
  Suggestion: confirm that the same-spec restriction is intended, and say so explicitly in t-1's description and in the §2b prompt text ("a deferred edge always files a new [[deferred]] in this spec; never point it at an existing item"). Alternatively, resolve against `deferredByID(root)` as `absorbedProblems` already does.

- [granularity / risk] t-6 must fit §2b into `assets/prompts/spec.md`, which is at 13,445 B against the 15,000 B `promptByteCap`. That leaves 1,555 B of headroom. In that space, §2b must carry: the edges command, the cap wording ("2–3", "one per turn", "never walk all eight"), all eight class names, the three outcomes, the `dross deferred new-id` minting step plus the same-id instruction, the must-NOT path ("never X when Y", "accept / reword / drop", dropped → dismissed or deferred, never covered), the no-minimum and non-applicable-is-dismissed rules, and the resolved-skip rule. §5 also gains an [[edges]] example and an `id` on [[deferred]]. TestSpecPromptBranchesFetchTheirPartial requires the common path to fetch nothing, so §2b cannot move into a partial. If the section runs over, the only option is trimming existing text, which risks breaking the TestPromptInstructionsConserved rows. The plan has no fallback for this.
  Suggestion: in t-6, draft §2b first and measure it with `wc -c` before writing the tests, and name ahead of time which existing spec.md prose can be shortened without touching conserved rows (fenced `dross`/`git` lines, `- **…**` lead-ins, inline `dross …` spans).

- [test-contract / correctness] t-4's gate loads "the current phase's spec.toml", meaning `state.current_phase`. But plan.md §0.3 resolves the phase to plan from `$ARGUMENTS` first and falls back to current_phase only when none is given, and plan.md never sets current_phase. Running `/dross-plan <other-id>` while current_phase points elsewhere therefore checks the wrong spec's edges. The planned status is already written against current_phase, so the existing mismatch carries over into the gate. As a result, c-7 ("refuses while the phase's spec has an unresolved edge record") only holds when the plan target equals current_phase. No t-4 contract case covers a plan target that differs from current_phase.
  Suggestion: either note in t-4 that the gate assumes target == current_phase and add a contract line covering that scope, or state the limitation in the t-4 description so verify does not read c-7 as unconditional.

## NOTE
- [granularity] t-1 (5 files) and t-5 (5 files) both reach the 5-file split threshold. In both, the extra files are filing and regression bookkeeping: `not_paths.txt` and `deferred_test.go` for t-1, `README.md` and `not_paths.txt` for t-5. Each task stays within one layer. Splitting either one would be an artificial split, so none is recommended.
- [coverage] Every criterion is covered: c-1 (t-5, t-6), c-2 (t-1, t-2, t-6), c-3 (t-1, t-3), c-4 (t-6), c-5 (t-1, t-3, t-4), c-6 (t-5, t-6), c-7 (t-4). Nothing in the plan contradicts edge_storage, deferred_link (apart from the scope narrowing flagged above) or zero_edges.
- [wave order] Every wave-2 and wave-3 dependency is real: t-3, t-4 and t-5 call t-1's EdgeProblems/EdgeStatus, and t-6 needs t-2's and t-5's verbs to resolve through root.Find. Tasks in the same wave touch no common files (README.md and not_paths.txt are split across waves 1 and 2).
- [scope] On the extend path, §2b proposes only *open* classes. A record that already exists but is unresolved (for example a hand-edited dismissal with no reason) is never re-surfaced by §2b and is caught only by §6's `dross validate`. This is acceptable because §6 says to fix validate errors, but the repair happens late in the session.
- [design] t-3 checks edges in complete phases as well. That differs from the precedent in `absorbedProblems`, which skips complete phases because their deferred items "go on living". The difference is justified: edge links are spec-local, and no verb deletes [[deferred]] entries. The consequence is that hand-deleting a linked [[deferred]] from a completed spec will fail validate permanently.
- [rules] r-01 (`make install` before relying on prompt or Go changes) is not violated by any task. To dogfood §2b live, though, the binary must be re-installed so `dross phase edges` and `dross deferred new-id` exist on PATH. The t-6 tests run through root.Find and do not depend on the installed binary.
- [strength] One rule set: validate (t-3), the state gate (t-4) and `phase edges` (t-5) all call t-1's EdgeProblems/EdgeStatus. t-4's contract requires the refusal text to equal validate's line, minus the prefix, which keeps the three from drifting apart.
- [strength] t-1 includes a regression guard: EnsureIDs (which re-saves through phase.Spec) must leave [[edges]] intact. This matters because LoadSpec is non-strict and a struct without the field silently drops the table. t-1 also adds a corpus test over every checked-in spec, with a non-empty-glob guard, which proves c-5 on real data rather than on a fixture alone.
- [strength] t-5 moves class hints and the resolved/open partition out of the prompt into a `--json` report. That makes c-6 deterministic Go behaviour instead of something the prompt has to reason out, and keeps spec.md's byte cost down.

## Summary
The plan has full coverage, sound wave order and a single shared rule set, but three test contracts can never fail (t-1 omitempty, t-2 used-ids, and the t-6 replace path, which also hides a real behaviour gap), and these should be tightened before execution.
