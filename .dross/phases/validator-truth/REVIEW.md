## FLAG

- [normalisation-completeness] The round-2 resolution reached 11 of the 13 config-enum normalisation sites in production code. The two misses are the milestone_mode *consumers*: `internal/forge/youtrack.go:185` and `internal/forge/jira.go:227`, both `switch strings.ToLower(strings.TrimSpace(mode))`. They are semantically identical to `configenum.Normalize` today, so nothing breaks — but they are the exact sites c-4 names ("because board sync lowercases and trims before matching"), and the stated decision was that Normalize becomes the single normalisation *by construction* so no site can drift. As a consequence, milestone_mode is the one enum of the four named in c-2 whose accept-set (`MilestoneModesFor`) has no divergence guard: t-10 scans `ship/{open,comment,merged}.go`, `forge/forge.go` and `project/remote.go`, never `jira.go`/`youtrack.go`.
  Suggestion: either add those two switches to t-7's Normalize sweep and to t-10's scanned-function list, or record in t-10's description why milestone_mode dispatch is deliberately left unguarded.

- [stale-literal-lists] `internal/ship/open.go:51`, `comment.go:44` and `merged.go:30` each carry `unsupported provider %q (expected github | forgejo | gitea | gitlab)`. The moment t-3/t-4 add the bitbucket arms, all three messages are false. No task derives them from `ShipProviders`, and t-10's guard reads case-clause literals, not message strings, so nothing catches it. The plan fixes precisely this stale-message problem in doctor (t-6: "if the message stops listing private-token | bearer | basic"), in `issue.go` (t-7: `TestIssueEnableNoteListsConfigenumSet`) and in `forge.New` (t-7) — ship is the one dispatch surface left hand-typed, in a phase whose premise is that hand-typed accept-lists lie.
  Suggestion: fold `ShipProviders.List()` into those three error strings under t-3/t-4 and add a contract line mirroring t-7's note test.

- [test-contract] t-1's "if the three empty-value policies are collapsed into one rule, `TestEmptyIsAcceptedAsDefault` fails" does not say which three, and the test name asserts the opposite of the contract's intent — a single blanket "empty is accepted". The policies genuinely differ: empty `auth_scheme` → private-token default (accept), empty `milestone_mode` → version default (accept), empty `[board].provider` → today doctor prints `✗ [board].provider = "" is invalid` (reject), empty/`none` ship provider → no remote. If `Set.Has("")` ends up uniformly true, t-6's rewritten board-provider check silently starts accepting an empty provider, and no t-6 contract line guards that regression.
  Suggestion: name the three policies in the description and add a t-6 contract line pinning "empty `[board].provider` still exits non-zero".

- [cross-field-gap] t-1 puts basic in one global `AuthSchemes`, so after t-6 doctor blesses `[remote].auth_scheme = "basic"` on *any* remote. Only the bitbucket path implements it: ship's `gitlabAuthHeader` (`open.go:229`) still falls through to `PRIVATE-TOKEN` for anything that isn't `bearer`, and the github path shells out to `gh` and ignores the scheme entirely. So gitlab + basic + a populated `auth_user` passes doctor clean and 401s on every ship — a provider/scheme combination that fails at runtime and is not reported, which is c-5's own wording. t-9's four warnings cover only *empty* `auth_user`; t-10's guard covers provider switches, not scheme handling. This extends pre-existing looseness (doctor already accepted `bearer` on a github remote) rather than regressing an invariant this phase established, hence flag not blocker.
  Suggestion: add a fifth t-9 warning — `auth_scheme = basic` with a remote provider that has no Basic dispatch — or scope the accept-set per provider via an `AuthSchemesFor(provider)` helper in t-1.

- [undeclared-symbol] t-7 states "forge.New's expected-provider message is generated from the set restricted to REST backends". t-1 exports `BoardProviders`, `MilestoneModes`, `AuthSchemes`, `ShipProviders`, `MilestoneModesFor` and `BoardRequiresBaseURL` — no REST-backend subset, and no rule that derives `{forgejo, gitea, gitlab}` from `BoardProviders`, which also holds youtrack/jira/github. t-7 cannot add one: `configenum.go` is not in its files list. The implementer's only route is a literal exclusion inside `forge.go`, i.e. a second hand-maintained list, which is the thing c-2 exists to remove.
  Suggestion: add the REST subset (or a `ForgeRESTProviders` set / `IsRESTBackend` helper) to t-1's exported surface so t-7 consumes rather than re-derives it.
