## BLOCKING
- [locked-decision] The repo's settings do not let GITHUB_TOKEN open a pull request, and locked `bump_ci` depends on it doing exactly that. `gh api repos/Rivil/dross/actions/permissions/workflow`, checked live today, returns `{"default_workflow_permissions":"read","can_approve_pull_request_reviews":false}`. With that setting off ("Allow GitHub Actions to create and approve pull requests"), the `gh pr create` in scripts/pin-bump-pr.sh fails with "GitHub Actions is not permitted to create or approve pull requests". The job's own `pull-requests: write` does not override a repo-level setting. No in-phase proof can catch this: TestPinBumpPRUpdatesOpenPR uses a fake gh, and `live_proof` defers the first real run until v1.7 is on main. This is the same kind of problem as the previous review's BLOCKING (a GitHub-side refusal of GITHUB_TOKEN that no test sees). As written, c-10 passes in-phase and fails on its first live run.
  Suggestion: the user has to decide. One option is to enable the setting (`gh api -X PUT repos/Rivil/dross/actions/permissions/workflow -f default_workflow_permissions=read -F can_approve_pull_request_reviews=true`). That also lets any workflow's GITHUB_TOKEN approve PRs, which matters little while main has no branch protection. If enabled, record the dependency in pin-currency.yml's header the way dependabot.yml records the settings it relies on. The other option is to reopen `bump_ci`. Either way, t-10 should say which.
