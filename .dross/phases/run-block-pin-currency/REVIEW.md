# Plan Review — run-block-pin-currency

Reviewed: 2026-09-29
Plan: 10 tasks across 5 waves

## BLOCKING
- [locked-decision] t-9 cannot push the bump branch for two of the five pins it bumps. The plan follows locked decision `bump_ci` (the job-scoped GITHUB_TOKEN pushes the branch), but GitHub rejects any GITHUB_TOKEN push that changes a file under `.github/workflows/`. The error is "refusing to allow a GitHub App to create or update workflow … without `workflows` permission", and `workflows` is not a permission the `permissions:` block can grant. setup-node `node-version:` lives in ci.yml and goreleaser `version:` lives in release.yml, so any bump that touches either one fails at `git push`. node-version is the pin c-8 says is stale today (24.20.0 and 24.21.0 are both more than 7 days old), so the first live bump run will fail. No in-phase test can catch this: TestPinBumpPRUpdatesOpenPR uses a fake gh, and `live_proof` puts off the first real push until v1.7 merges to main.
  Suggestion: the plan cannot fix this without the user. Reopen `bump_ci` in spec.toml. Options include moving the two pins out of `.github/workflows/` (for example setup-node's `node-version-file:`) or accepting an App token, which the decision's "no long-lived write credential" reasoning currently rules out. Then re-plan t-9 and t-7 against the new decision. Shipping as written means c-10 passes in-phase and fails on its first live run.

## FLAG
- [test-contract] t-5 has no step that resolves a `go install` package path to its module path. The proxy only serves module roots: `proxy.golang.org/golang.org/x/vuln/cmd/govulncheck/@v/list` and `…/go-gremlins/gremlins/cmd/gremlins/@v/list` both return 404 today (checked live). A resolver that queries the install path as written sees govulncheck and gremlins as permanently `unknown`, which leaves the strict cron red every week. TestFetchParsesEachUpstream feeds canned bodies straight to the module URL, and TestFetchFailuresAreUnknown lists 503, timeout, closed listener and malformed JSON but not 404/410. The same gap applies in doctor, where most `go install` pins in other repos are `/cmd/…` subpackages.
  Suggestion: state in t-5 that it resolves the module path by walking up the package path (or uses a fixed mapping for the dross-only sites). Add a contract where a stub answers 404 on `pkg/cmd/x` and 200 on `pkg`, plus 404 on every prefix, which should give `unknown`.
- [test-contract] t-5's golang.org/toolchain list is not semver-shaped. It interleaves rc builds and per-platform duplicates (`v0.0.1-go1.27rc1.linux-amd64`, `v0.0.1-go1.27.0.linux-amd64`, …). t-2's pre-release contract only uses semver pre-release shapes (`v1.9.0-rc.1`, `24.20.0-beta`). A strict parser that meets `go1.27rc1` returns "malformed", which means `unknown`, which fails the cron. A loose parser could rank an rc wrongly.
  Suggestion: make the canned toolchain body in TestFetchParsesEachUpstream include rc entries and several platforms. Assert that rcs are dropped and each version appears once.
- [test-contract] No contract pins that an `info` verdict passes strict mode. TestPincheckExitCodes and TestCheckModes only cover stale, unknown and all-current. This is live from day one: Node v26.10.0 exists, so the Node 24 pin classifies as info alongside stale. If Check treats info as failing, the cron is red with nothing to bump, and t-10's "re-run until it exits 0" never ends. `stale_line` (locked) says off-line releases "never fail".
  Suggestion: add an info-only verdict to TestCheckModes (it passes both modes) and to TestPincheckExitCodes (exit 0, info line printed).
- [test-contract] t-1 reports goreleaser `~> v2` as an "unpinned site", but no task defines what verdict an unpinned site gets. c-2's verdicts are current/stale/unknown, and t-2 adds info. t-6 (strict mode) and t-8 (doctor) are both silent on it. The same question applies to `node-version: '24.x'` and `go install x@latest`, which doctor will meet in other repos.
  Suggestion: say in t-6 and t-8 how an unpinned site is classified and whether it fails strict mode or counts as a doctor issue. Pin that in TestCheckModes.
- [test-contract] t-1's scanner contracts only cover the shapes the dross repo uses, but c-9 runs it in any dross-managed repo. Untested shapes that doctor will meet: `.github/workflows/*.yaml` and `action.yaml` (the plan's globs are `*.yml` only), multi-line `run: |` block scalars (the hard part of "run-block scope" for a line scanner), `node-version: ${{ matrix.node }}`, and `node-version-file:`.
  Suggestion: extend the TestScanFindsEverySiteKind fixture to include `.yaml` workflows and a `go install` inside a `run: |` block. Add a case to TestScanIgnoresNonRunInstalls showing that a `${{ … }}` node-version is not reported as a pinned version.
- [test-contract] t-6's TestEveryPinSiteIsChecked does not say where its "independent broad pattern sweep" stops. A broad version regex over `.github/**` and go.mod matches sites Dependabot owns: every `uses: …@sha  # vX.Y.Z` comment, every go.mod `require` line, and the `go 1.27.0` directive. If the sweep stays broad, the test fails on day one or grows an ad-hoc allowlist. If it copies the scanner's own regex, it is no longer independent.
  Suggestion: name the exclusion set in the contract (uses: lines, go.mod require and go directives, testdata/) and the inclusion rule the sweep uses. Only two non-test Go consts carry `@X.Y.Z` today (gremlinsPin, strykerPin), so the Go-const half is easy to pin exactly.
- [test-contract] t-8's TestPinVerdictParity lives in `internal/cmd`, which cannot import `cmd/pincheck` (package main). The contract does not say how it reaches "cmd/pincheck's path". If both paths come down to `pincheck.Check(…, strict)` versus `pincheck.Check(…, lenient)`, the test only checks the shared function and says nothing about the cron's scan/resolve wiring. c-9 requires that "both paths classify a fixture pin identically".

- [test-contract] t-8's TestDoctorPinSectionUsesSeam says "the doctor suite completes without a network call", but one test cannot observe the whole suite. `Doctor()` runs from at least 10 test files in internal/cmd (consent_surface, trust, friction_window, hostile_config, gitseparator_remaining, …), not just the doctor_*_test.go files. - [test-contract] t-9 does not specify how the check job and bump job are wired, or what the script does when nothing changed. The check job exits non-zero on stale, so a plain `needs: check` would skip the bump job at exactly the moment it is needed. TestPinBumpPRUpdatesOpenPR has no case showing that an empty diff pushes nothing and opens no PR. The contract fakes `gh` but not `git push`.
  Suggestion: pin the bump job's `needs`/`if` in TestPinCurrencyPermissions or TestPinCurrencyDispatchesCI. Add a no-diff case to TestPinBumpPRUpdatesOpenPR (no push, no `gh pr create`), and name how push is faked (a local bare remote).
