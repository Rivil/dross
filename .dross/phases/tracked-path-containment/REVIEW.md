NOT CLOSED — narrowly. The *rule* is fixed; the *placement it depends on* is contradicted by the task that implements it.

What is fixed: t-10 now defines guarded as "calls pathfence.\* OR calls a routing function named by a Consumed entry in pathfence.Fields", t-2 line 7 declares changes.TaskRecord.Files and verify.Scope.Files Consumed naming verify.ValidateRecorded, and t-5's description no longer claims mutationCandidates is a scanned join site — it now says outright that mutationCandidates "takes files []string and reads no field selector, so it is invisible to t-10's scan either way". That correction is accurate: `mutationCandidates(repoDir string, files []string)` at internal/cmd/verify.go:1189 reads no selector.

What is not fixed: the amendment only works if `verify.ValidateRecorded` is called **from the two reader functions themselves**. t-10 asserts exactly that (line 2: "the `dross verify` RunE closure and collectDetached both pass by calling verify.ValidateRecorded"). t-5 — the task that writes the code — describes the opposite placement: "phaseScope (verifyscope.go:24) changes from returning \*verify.Scope to (\*verify.Scope, error) ... and both verify entry paths propagate". If the readers called ValidateRecorded directly, phaseScope would need no error return at all and the 8 call sites in verifyscope_test.go would not move. The natural reading of t-5 is that ValidateRecorded is called *inside* phaseScope — and under that placement the RunE closure (verify.go:57-146, reads `rec.Files` at :74, `scope.Files` at :90, `filepath.Join` at :57/:61) and collectDetached (verify.go:518, reads `r.Files` at :585, `scope.Files` at :588, `filepath.Join` at :565/:569) call `phaseScope`, not `ValidateRecorded`, and t-10 line 2 goes red on correct code — the original finding, verbatim. `phaseScope` itself is not a rescue: it reads no declared selector and calls no filepath.Join/os.\*, so it is not a join site and cannot be the named routing function.

Also unresolved: t-5's own sentence "The refusal therefore precedes phaseScope" contradicts the phaseScope signature change one clause earlier. The plan is asserting both placements at once.

This is one sentence away from closed: t-5 must say where the ValidateRecorded call goes. If it goes in the two readers, say so and justify (or drop) the phaseScope signature change. If it goes in phaseScope, t-10's routing-function arm has to name phaseScope, and t-2's Consumed entries with it.

Satisfiability check requested: for changes.TaskRecord.Files and verify.Scope.Files, t-10's vacuity guard ("at least one join site per Consumed entry") IS satisfiable — both selectors are read inside functions that also call filepath.Join (verify.go:74/:90 and :585/:588). t-10's line 5 ("a Consumed entry whose named routing function does not appear among the guarded join sites fails") is satisfiable only under a charitable reading; see FLAG. And the check does not extend to the third path-shaped field the phase actually guards — see BLOCKING.

## BLOCKING

- [test contract] changes.RedProof.Doc — the third field this phase actually guards — has no coherent disposition, and t-10 goes red on correct code either way. t-2's named minimum includes changes.RedProof.Doc but pins no Disposition for it (it pins only phase.Task.Files, the three tag false positives, and the two Consumed verify entries). Trace it:
    - The only non-test function that reads the `changes.RedProof.Doc` selector is `discoverRedProofPins` (internal/cmd/redproof.go:118-139): `Doc: c.RedProof.Doc` at :133, with `filepath.Join` at :119 (inside the Glob) and `filepath.Base`/`filepath.Dir` at :126. By t-10 line 1's definition — reads a declared selector AND calls filepath.Join — it is a join site.
    - Neither site t-8 guards reads that selector. `applyRedProofRepoint` (redproof_repoint.go:137) reads `p.Doc` on `redProofRepointPlan`, a cmd-local struct with no Fields entry — excluded by t-10's own receiver-type rule. `redProofDocSHA(repoDir, doc string)` (redproof.go:145) takes a plain string. doctor.go:604 passes `pin.Doc` on `redProofPin`, also cmd-local.
    - So: declare it Consumed, and `discoverRedProofPins` fails line 1 as an unguarded join site (it calls neither pathfence nor whatever routing function is named), while the vacuity guard has no guarded join site to point at. Declare it NotConsumed, and line 4 fires — "declared not-consumed but discoverRedProofPins opens it" — and the declaration also contradicts artifact_scope, since t-8 exists precisely to route this field through the shared check.
  The underlying cause is that t-10's join-site test is co-occurrence, not dataflow: any filepath.Join anywhere in the function counts, and discoverRedProofPins' Join builds the glob, not the doc path. That shape will keep producing this failure for fields whose value is copied into a local struct before it is opened — which is what all three red-proof doc readers do.

## FLAG

- [antipattern: missing files] t-6 names internal/cmd/task_lifecycle_test.go for its `dross task add --files ../x` assertion; that file does not exercise `dross task add`. The tests that do are in internal/cmd/task_test.go. Swap the file.

- [test contract] t-1 line 10 asserts ``InTree(`a\b/../c`)`` returns `("a/c", true)`. With the implementation t-1's description states — filepath.ToSlash then path.Clean — that holds on Windows only. On darwin filepath.ToSlash is the identity, so `a\b` stays one segment, `..` pops it, and path.Clean returns `"c"`. The line as written fails on the machine the suite runs on. The platform-independent form is the one verify.NormalizePath already uses (scope.go:328: `strings.ReplaceAll(..., "\\", "/")`, with the comment at :323-325 explaining exactly why it is unconditional rather than by platform). Either the description or the contract line has to move.

- [test contract] t-10 line 5 is unsatisfiable under its literal reading. "A Consumed entry whose named routing function does not appear among the guarded join sites fails" — `verify.ValidateRecorded` reads no selector and, per t-5, does no I/O (internal/verify stays I/O-free), so it is not a join site at all, guarded or otherwise. Every Consumed entry fails. The intended reading is presumably "does not appear as the guard of at least one guarded join site"; say that.

- [test contract] t-3 lines 3 and 4 are not writable against the command surface. All eight containedPath call sites pass a string literal as `name` — "findings.toml" (security.go:45,152; quality.go:39,122), "spec.toml" (security.go:160; quality.go:130), "report.md" (security.go:204; quality.go:150). The caller-controlled input is `runDir` (args[0]), never the name. So "a scan-run ledger name of `../main.go` refuses and leaves no file at Join(runDir,'..','main.go'), asserted by stat-ing the parent directory before and after the run" has no code path to drive it, and "an absolute ledger name `/tmp/x/spec.toml`" likewise. Both can only be asserted by calling pathfence.Contain directly, which is t-1's contract already. (The "finding-derived name" framing comes from containedPath's own doc comment at security.go:185-186, which overstates what the code does.)

- [antipattern: unverifiable claim] t-10's receiver-type disambiguation cannot be built from the toolset t-10 names. "go/parser + go/ast, no x/tools" gives no type information, and resolving `c.RedProof.Doc` or `rec.Files` to a declaring package's type requires type checking. The cited precedent does not do this: internal/cmd/enum_divergence_test.go imports go/types solely for `types.ExprString` (:89, :127), a source printer, not a checker. Implementing the stated rule needs go/types + go/importer (or x/tools/packages); implementing it with ast alone means a local-declaration heuristic, which is a different and weaker rule than the one the plan promises and the one contract line 3's fixture will be written against.
