## FLAG
- [locked-decision / antipattern] t-5's "new doctor section" doesn't account for doctor.go's existing "Foundational files" block (doctor.go:57-76), which already detects missing `project.toml`/`rules.toml` and already prints a remediation hint — but that hint points at `dross ship recover` and `RepairHint` (`run \`dross onboard\``), not at the new `dross repair`. Worse: that block `return`s early (doctor.go:73-75) whenever project.toml or rules.toml is missing, before any later section — including t-5's new one — ever runs. Since c-1/t-1 explicitly puts project.toml/rules.toml in `dross repair`'s detection scope, the plan needs to say whether t-5 rewrites that existing block's hint text, or leaves two different remediation messages for the same missing-file case (one naming `ship recover`/`onboard`, a new one — never reached for this exact case — naming `repair`). As written, c-6 ("doctor... points at `dross repair`") will not fire for the specific project.toml/rules.toml-missing case the criterion's own file list calls out.
  Suggestion: have t-5 explicitly state whether it edits the existing Foundational-files block's hint, or scope c-6 to note it only applies to the non-foundational clobbers (phase dirs, milestone tomls, mid-file diffs) that don't short-circuit before reaching it.

- [locked-decision / antipattern] Every command that resolves its root via `FindRoot()` (root.go:112) already calls `ensureState`, which writes a fresh blank `state.json` (Version seeded from project.toml, empty History/CurrentPhase) the instant the file is absent — "the write only ever happens for an absent file" (root.go:107-111, state.go:263-279). If `dross repair` (t-4) resolves its root the same way every other command does, `state.json` will never actually be observed "missing" by repair's own top-level flow — by the time repair's logic runs, `ensureState` will already have materialized a blank one. c-3 and t-2 do still work against this (a blank file is "clearly stale" and reconstructState can still fix it), but the plan/test_contract talk about "missing" as a distinct, reachable case without addressing that at the CLI-integration level it collapses into "stale-and-blank" before repair's code ever sees it. t-2's own unit tests (calling reconstructState directly) aren't affected, but t-4's integration test contract should say which of the two states it's actually fixturing.
  Suggestion: have t-4's test_contract or t-2's description note explicitly whether repair uses `LocateRoot` (no materialization) or `FindRoot` (materializes first), so "missing" isn't tested as an integration scenario that can't occur.

- [test-contract completeness] t-1's `covers` lists c-5 ("healthy .dross is a safe no-op"), but none of t-1's three test_contract lines exercise the no-findings/no-op path — that behavior is only actually asserted in t-4's contract ("no --apply and no findings prints 'nothing to repair'"). Coverage-checking tooling (or a future `dross verify` criterion→test mapping) that expects each covering task to carry its own evidence will find t-1 claims c-5 with nothing to point at.
  Suggestion: either drop c-5 from t-1's covers (leave it solely on t-4, which does test it) or add a no-op assertion to t-1's own contract.

- [test-contract completeness] t-1's description says it detects clobbers across "project.toml, rules.toml, milestone tomls, phase spec.toml/plan.toml", but its test_contract only names project.toml and phase spec.toml scenarios — rules.toml and milestone tomls are asserted nowhere in the plan (t-4's contract doesn't name them either). If the detector is generic over a path list this may be a non-issue, but the plan gives no evidence milestone-toml/rules.toml paths are actually wired into that list.
  Suggestion: add one contract line (in t-1 or t-4) naming a milestone toml or rules.toml case, or confirm the detector takes an enumerated path set that visibly includes them.

- [antipattern] No task touches `README.md`. This repo has an established convention of README/behavior-parity tests for user-facing commands (`TestReadmeDocumentsInstallAndUpdate`, `TestReadmeDocumentsBaseTruthSurfaces`, `TestDoctorFoundationalDocMatchesBehaviour` in gitignore_test.go/readme_doc_test.go) and a recent "readme-truth-pass" milestone per project history. A new top-level `dross repair` command with its own `--apply` flag and dry-run default is exactly the kind of surface that convention exists to keep documented, and none of the existing parity tests happen to gate on it, so it can ship silently undocumented.
  Suggestion: add a README doc line to t-4 (or a short follow-up), even though no test currently forces it.
