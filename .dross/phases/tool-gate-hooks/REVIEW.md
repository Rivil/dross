# Plan Review — tool-gate-hooks

Reviewed: 2026-10-02
Plan: 18 tasks across 4 waves

## BLOCKING
- [locked-decision] t-9 and t-16 conflict with the locked `green_run_definition` decision ("a full `dross test` run over every declared lane") in any repo that declares lanes. A bare `dross test` never runs lanes: `internal/cmd/test.go:281` only takes the lane path when `len(files) > 0 && len(TestLane) > 0`, so otherwise it runs `runtime.test_command` alone. That causes two problems:
  (a) In a repo with both test_command and lanes, t-9 records "a selector-free test_command run" as full, and t-16 tells execute.md to run "a bare `dross test` before `git commit` when lanes are declared". The green then covers zero declared lanes. A Go test_command plus a web lane would let a commit touching web/ pass on a Go-only green. The decision's own "why" rules this out ("a partial run proves less than the tree being committed").
  (b) In a lanes-only repo (no test_command, the shape test.go's comments say lanes "most exist to serve"), a bare `dross test` fails at `requireExecConsent` on the empty command. A lane run only counts as full if every lane runs unscoped, but `--files` makes any lane with a `selector` derive scoped arguments (`lane_plan.go` laneRunLine). So when any lane declares a selector, the plan has no way to produce a green at all. t-10's carve-out only covers "neither test_command nor lanes", so every code commit in such a repo is refused until a human runs `gate off`. t-9's contract also has no positive test showing that an all-lanes unscoped green run records anything. It only checks partial runs that record nothing.
  Suggestion: make t-9, t-10 and t-16 agree on what a full run is in a laned repo. Options: bare `dross test` runs every declared lane unscoped when lanes exist, or test_command counts as full only when no lanes are declared. Then add the matching positive contract to t-9 (an all-lanes green records a tree equal to `treefp.Candidate()`) and a lanes-only case to t-10.

## FLAG
- [test-contract] t-17's last contract claims "dropping the gate pair also fails TestOnboardEnsuresSameHooks's byte-parity". It won't. That test (`internal/cmd/onboard_test.go:78`) compares init's settings.json to onboard's, and both go through the same `ensureUserHooks`. Removing the gate pair from `ensureUserHooks` changes both outputs the same way and parity stays green.
  Suggestion: drop the claim, or have the contract require that the init test (or the onboard test) count exactly one `dross gate check` PreToolUse entry and one `dross gate record` PostToolUse entry.
- [test-contract] t-10 only specifies the refusal for "no green / stale green" ("naming a full `dross test`"). It says nothing about the common case where a green exists but the candidate ≠ the green tree because other paths are unstaged or untracked. t-2 makes this divergence deliberate, and execute.md/quick.md insist on `git add <specific files>`, never `-A`. Here the stated remedy loops: re-running `dross test` fingerprints the same WorkingTree, the candidate still differs, and the commit is refused again. c-2 requires the message to name the sanctioned path, and "run dross test" is the wrong one here.
  Suggestion: add a t-10 contract. When green.json exists but ≠ the candidate, the refusal must name the diverging paths and tell the agent to stage or clean them, not re-run `dross test`.
- [wave-order / risk] t-11's fixture capture is a go/no-go spike: "if it carries no answers in tool_response, stop and re-decide". Locked `pair_approval_signal`, c-5, t-13 and t-16 all depend on it, yet it sits in wave 2 behind a full wave of work, and t-13 runs beside it. Capturing a real PostToolUse payload also means temporarily wiring a dump hook into the user's `~/.claude/settings.json`. No file in t-11's list covers that, and it is a user-config change that needs the human's go-ahead.
  Suggestion: pull the capture into wave 1 (part of t-3 or a precondition note on t-4), say how the payload gets captured (a temporary user-level hook the human approves, then removed), and say where the fixture lives until t-11 consumes it.
- [wave-order] t-12 and t-13 are both in wave 2 and both edit `cmd/dross/main.go` and the regenerated golden `cmd/dross/testdata/cli_tree.txt`. Run in parallel, they conflict on the AddCommand list and the golden. Run sequentially, whichever lands second has to regenerate the golden.
  Suggestion: make t-13 depend on t-12, or note that the two run sequentially and the golden is regenerated after the second.
- [test-contract] t-1 sets `Partial=true` on an unbalanced quote, but no consuming task says what a gate does with a partial scan. Under `gate_error_posture`, a claimed-but-unjudgeable call should be refused, yet t-7 (secret-stream/secret-read) and t-10 (commit-green) never state whether a Partial command is claimed, refused or allowed. execute.md's commit is a heredoc message that often contains apostrophes, so a lexer slip there turns into either an ungated commit or a blocked one, with nothing pinning which.
  Suggestion: add one contract each to t-7 and t-10 fixing their Partial behaviour (for example: a Partial scan containing a `git commit` / secret-tool token refuses naming the parse problem, and one without passes).
- [antipattern] t-14's tamper-guard covers Edit/Write/MultiEdit of `.dross/gate/**` and `~/.claude/dross/gate-overrides.json`, but not Bash writes to the same files (`> .dross/gate/green.json`, `tee`, `cp`). t-1 already exposes redirect targets with fd attribution, so this would be cheap to cover. As planned, the guard blocks the tool an agent is least likely to use for a forged green or override, and leaves open the one it reaches for after a Bash refusal. `shell_detection_depth` puts deliberate evasion out of scope, but a direct `>` redirect is a "direct invocation", not obfuscation.
  Suggestion: either extend tamper-guard to Bash redirect, `tee` and `cp` targets via the t-1 scan, or state in t-14 that Bash writes are out of scope so the guard doesn't overclaim.
- [scope] t-14's override store is user-level (`~/.claude/dross/gate-overrides.json`), keyed by `{name, until}` with no repo. A human lifting `commit-green` or `pair-approval` for one repo silently lifts it in every repo and every concurrent session for up to 24h. For the always-on secret gates, global scope is natural. For the workflow gates it widens the escape well beyond what the human meant.
  Suggestion: key workflow-gate overrides by repo root (secret gates can stay global), or have t-15's `gate off` output and `gate status` state plainly that the lift is machine-wide.
- [over-fire] t-7 matches `id_* not *.pub` as a basename glob, and secret-read is always-on in every repo for every Read. That refuses ordinary source files such as `id_token.go`, `id_generator.ts` or `id_test.go`. The allow table only tests `id_ed25519.pub`, `envoy.yaml` and `main.go`, so nothing catches the false positive. The spec says "`id_*` private keys", which leaves room to narrow it.
  Suggestion: limit the default to key-shaped names (`id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519`, plus their `_sk` variants) or to paths under `.ssh/`, and add `internal/auth/id_token.go` to the Read allow table.
- [refusal-shape] t-3's refusal-shape contract requires every refusal to carry "a human can run `dross gate off <name>` in their own terminal". But gate-off-guard and tamper-guard are `Liftable=false`, and t-15 makes `gate off gate-off-guard` / `gate off tamper-guard` error. Their refusals would point the human at a command that refuses.
  Suggestion: make the hint conditional on `Liftable` in the t-3 contract, and assert that a non-liftable refusal leaves it out.
- [doctor/ensure interplay] `hooks.MergeHook` counts a command as present if any group under the event runs it, matcher-restricted groups included (`groupRunsCommand`). t-18 correctly flags "gate command only under a matcher-restricted group" as an issue. But the natural remedy, `dross hooks ensure`, will no-op on that file, and t-18 doesn't say what the issue line tells the user to do.
  Suggestion: have t-18's hidden-hook contract name a remedy that actually works (remove the matcher, or move the command to a matcher-less group), not `dross hooks ensure`.

## NOTE
- [coverage] All nine criteria are covered. c-4 (7 tasks) and c-2 (5 tasks) are covered from several angles.
- [strength] Collateral foresight is unusually good. t-6 moves handoff.md edits off Write before c-8 would refuse them. t-5 and t-16 bring ship/init/execute in line with the commit gate before it arms. t-18 seeds the four hooks in `chdir()` so the ~105 existing Doctor() calls stay green. t-12 keeps refusal text (secret paths) out of telemetry `err_detail`. t-3 builds a read-only locator because `FindRoot` writes `state.json` via `ensureState` (`internal/cmd/root.go`). t-2 pins `TestNoUnseparatedGitPositional`.
- [strength] Test contracts name exact inputs and the specific breakage: exit 1 vs 2 as Claude Code's fail-open boundary (t-12), 499/500/2000-byte shrink boundaries over every curated path (t-8), the exact case and whitespace variants of the approve label (t-11), and the heredoc-commit shape that must not leak a nested `cat .env` (t-1).
- [strength] t-11's spike-then-stop clause and t-17's ordering rationale both show deliberate risk sequencing. The ordering is partly moot, though: `make install` doesn't run `hooks ensure`, so nothing arms until someone runs it.
- [locked-decision] t-10's "silent with neither test_command nor lanes" carve-out isn't in c-4 or any decision. It's sensible, since no green can exist, but it changes c-4's observable contract. Record it as a spec decision so verify doesn't read it as drift.
- [granularity] t-12 and t-15 each touch 5 files, which meets the split threshold. In both, one file is the regenerated `cli_tree.txt` golden (plus a one-line AddCommand in t-12 and a README row in t-15). No split is warranted.
- [wave-order] t-16's `TestPromptCommitsSatisfyGreenGate` asserts t-5's ship.md step ("deleting ship.md's step (t-5) fails it"), but `depends_on` doesn't list t-5. Wave order (1 → 3) covers it.
- [spec-level] The spec's `.env*` default (c-7) makes secret-read refuse `Read .env.example` and `.envrc`. `.env.example` exists in barktime, sunday-rider, my-journal and feastahead/web, and reading it is a routine, honest way to learn a project's config keys. This is faithful to the spec, so it's not a plan defect. Raise it at spec level before execution if the refusal isn't intended.
- [spec-level] t-18 reads "effective settings.json" as the user-level file only (consistent with `hook_scope`). A project-level `.claude/settings.json` or `settings.local.json` with `"disableAllHooks": true` would still show ✓.

## Summary
The plan is careful and its contracts are among the most specific this repo produces, but it shouldn't proceed until t-9, t-10 and t-16 define a recordable full run for laned repos: as written, a test_command-only green passes in mixed repos and no green is possible in lanes-only repos with selectors.
