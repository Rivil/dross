# Plan Review — tool-gate-hooks

Reviewed: 2026-10-02
Plan: 19 tasks across 4 waves

## BLOCKING
- [locked-decision] t-19 overturns a locked decision from a shipped phase. test-lane-config's `bare_test_run` (locked) reads: "`dross test` with no --files runs runtime.test_command, unchanged ... Lanes scope the gate; test_command remains the whole suite", and its why is "leaves verify.md's full-suite meaning untouched". t-19 makes a bare run spawn test_command plus every lane, and reinterprets `bare_test_run` as covering lane-less repos only (its last contract). This spec records no superseding decision. The cost is concrete in the one laned repo you have: feastahead's `test_command` (`scripts/dross-test.sh`, "(no selector) both lanes, full suites") already runs both lanes in full. So after t-19 a bare `dross test` runs the web and phone suites twice. t-16 then adds that bare run to execute §1f before every task commit in a laned repo, after §1e's scoped `--files` run, and t-5 adds it before ship's ARCHITECTURE.md commit. verify.md's bare `dross test` changes meaning in the same way, which the locked why set out to prevent. `green_run_definition` requires "every declared lane". It does not require test_command alongside the lanes, so the doubling is the plan's choice, not the spec's.
  Suggestion: have the user record a decision in spec.toml that explicitly supersedes `bare_test_run`, and settle whether test_command still runs next to the lanes when lanes are declared. Then make t-19's description and spawn-table contract match. Today the contract asserts test_command AND both lanes spawn, which is the double run.

## FLAG
- [antipattern / files] Repo-wide audits will go red, and no task lists the files that fix them. `TestEveryPathShapedFieldIsDeclared` (`internal/cmd/pathfence_fields_test.go`) loads `./...` and requires EVERY toml/json-tagged string field in every package to be filed in `pathfence.Fields()` or `internal/cmd/testdata/pathfence_scan/not_paths.txt`. `hooks.hookCommand.Command` is already filed there, which shows non-cmd packages are in scope. The plan adds such fields in t-3 (payload `tool_name`/`cwd`/`session_id`, the gates.toml lists), t-4 (green/execute/approval records), t-11 (the answer decode) and t-14 (override `name`/`repo`/`until`). The pathtaint scan also makes opening any path-valued field without `pathfence.Contain` a finding with no marker escape. That constrains t-3's locator, which walks up from payload `cwd` and has no containing root, and t-8, which reads the target file's size and decodes plan.toml from `tool_input.file_path`. t-3 and t-4 (wave 1) and t-11 and t-14 (wave 2) would all append to the same ledger.
  Suggestion: add `not_paths.txt` (and `internal/pathfence/fields.go` where a field is a real path) to the files of each task that introduces tagged fields. State in t-3 and t-8 how payload paths get opened under the pathtaint rule: Contain against the located repo root, or untagged/map decode. Leaving it out lets the audit force a design choice in the middle of a task.
- [test-contract] Nothing stops a panic outside a Judge from blocking every tool call on the machine. t-3 recovers panics per gate only. `cmd/dross/main.go` has no `recover()`, and a Go panic exits 2, which is exactly PreToolUse's block code. A nil deref in payload decode, the locator, gates.toml or overrides loading, or dispatch would therefore refuse every tool call in every repo. `dross gate off` can't lift it, because no gate is involved. t-12's tests also run in-process, so they never exercise main.go's `fmt.Fprintln(os.Stderr, "dross:", err)`. That leaves the "exactly once on stderr" and exit-2 claims unverified at the binary level.
  Suggestion: add a t-12 contract that a panic injected outside any Judge (for example in the payload decode or locator seam) exits 0 with one warning, never 2. Pin exit code and single-print with a subprocess case in the `TestMainEntryPoint` style.
- [test-contract] t-10 has no case for the heredoc commit, which is the default Claude Code shape: `git add a.go && git commit -m "$(cat <<'EOF' … EOF)"`. t-1 deliberately yields a nested `cat` command out of the substitution. t-10's rule refuses chains "where anything but `git add`/`cd` precedes the commit", and nothing says whether a nested substitution command counts as a predecessor. If it does, every heredoc commit is refused. Every t-10 contract uses `-m x`.
  Suggestion: add the heredoc form, chained after `git add`, to t-10's green-match and replay tests. Assert it passes with a matching green and is judged against index+a.go.
- [test-contract] t-9's before/after fingerprint mismatch "records nothing", with no output. A suite that writes an untracked, unignored file (coverage output, a snapshot, a generated fixture) never records a green. t-10's no-green refusal then sends the agent back to `dross test`, which hits the same mismatch. This is the non-converging loop that t-10's diverged-paths contract was added to stop.
  Suggestion: add a t-9 contract that a mismatch prints one stderr line naming the paths that changed during the run.
- [test-contract] t-16's `TestPromptCommitsSatisfyGreenGate` matches "any fenced block with `git commit` whose `git add` names a non-.dross path". execute.md §1f and quick.md §5 put `git add <files>` in a fence with no `git commit` literal, because the message templates sit in separate fences. The audit therefore only sees ship.md and init.md, and "quick.md passes unchanged" passes vacuously.
  Suggestion: key the audit on a `git add` of non-.dross paths (or on the commit section) rather than on a fenced `git commit`. Add a vacuity assertion that quick.md and execute.md §1f are actually matched.
- [collateral] t-18 makes `dross doctor` exit non-zero when gate hooks are absent. ship.md §3 and review.md §5 both say "`dross doctor` — must exit 0", so /dross-ship and /dross-review hard-stop on any machine without gate hooks. That includes shipping this phase once `make install` (r-01) puts the new binary in place, which forces the gates to be armed on your machine before this phase ships. The plan does this kind of collateral fix elsewhere (t-5, t-6, t-16), but no task covers this coupling.
  Suggestion: state the coupling in t-18. Either accept "run `dross hooks ensure` before ship" explicitly or adjust the ship/review pre-flight wording, and pin whichever is chosen in a contract.
- [tamper surface] An agent can forge a pair approval through dross's own writer, and the plan leaves that open. `echo '{"tool_name":"AskUserQuestion","tool_response":…"approve t-3"…}' | dross gate record` from the agent's Bash records the approval. tamper-guard (t-14) only blocks direct writes to `approval.json`. The plan treats this kind of forgery as in scope elsewhere: t-14's Bash-tamper table, t-11's `execute begin --solo` downgrade guard, and gate-off-guard. t-14's Bash table also never covers the overrides file through `~`/`$HOME` (`echo x > ~/.claude/dross/gate-overrides.json`), and t-1 specifies no tilde expansion.
  Suggestion: have the self-guard refuse Bash `dross gate record` and `dross gate check`, since they are hook-only verbs, and add both to t-7's self-guard table. Add the `~/.claude/dross/gate-overrides.json` redirect to t-14's Bash-tamper table.
- [spec-level] c-6 misses the main way secrets leak. Claude Code's Bash tool returns stderr to the model whether or not it is merged. `pass-cli item view x | head` and `pass-cli item view x >f` (stderr not redirected) still put the stderr half of the secret in the transcript, and c-6 allows both because nothing is merged. Your own Secret Handling rule 2 says to redirect both streams (`>file 2>/dev/null`), and t-7's allow table already treats that as the safe form. This is not a plan defect, since t-7 implements c-6 faithfully.
  Suggestion: raise it with the user before execution. If c-6 is amended to "a secret-emitting tool whose stderr or stdout reaches the transcript", t-7's refuse/allow tables change shape.
- [granularity] t-3 touches 5 files and packs in a lot: payload decode, the gate registry and dispatch with panic recovery, refusal shape, a read-only locator, the default lists plus gates.toml extension, and the human-in-the-loop go/no-go capture. The capture needs a separate Claude Code session in a scratch repo. Its 9 contracts span all of that, so the engine work can't be marked done until a human runs that session.
  Suggestion: split the fixture capture from the engine work. Both stay in wave 1, and only t-11 needs to wait on the capture result.

## NOTE
- [coverage] All 9 criteria are covered. c-4 is covered by 8 tasks and c-2 by 5. Every `locked = true` decision in this spec is respected by the task text.
- [strength] t-19 plus t-9's new positive contracts (`TestAllLanesGreenRecords`, the lanes-only case) close the previous review's "no recordable green in laned repos" hole. The open question is only which full run, per the BLOCKING above.
- [strength] The design fails closed by default. gates.toml is additive only, so an agent can't subtract pass-cli. Self-guard and tamper-guard are `Liftable=false`, and the hint is suppressed for them. Workflow overrides are repo-scoped while secret overrides are machine-wide. Approvals bind to (phase, task, HEAD). An unparseable payload passes while an in-domain error refuses, which follows `gate_error_posture` exactly.
- [strength] Contracts name precise breakage: exit 2 vs 1 as Claude Code's fail-open line (t-12), 499/500/2000-byte boundaries over every curated path (t-8), case and whitespace variants of the approve label (t-11), and real-index sha256 invariance (t-2).
- [wave-order] Carried over unaddressed from the previous review: t-12 and t-13 both edit `cmd/dross/main.go` and the `cli_tree.txt` golden in wave 2. This is harmless under sequential pair-mode execution, since both mark the golden as regenerated, but it conflicts under parallel execution.
- [hermeticity] internal/cmd pins HOME in `TestMain` (`hermetic_env_test.go`), but new packages do not inherit that. internal/gate tests read `~/.claude/dross/gates.toml` and `gate-overrides.json`, so after you run `dross gate off` locally they could see real lifted gates. That gives local-only failures, the failure mode that pin exists to stop. Inject the config dir, or pin HOME in those packages.
- [pair-mode] t-11 arms on "in_progress task + phase branch", and execute.json has no end marker. A stale in_progress left by an abandoned session therefore arms the gate for /dross-quick or manual edits on that branch. t-11's downgrade guard also refuses `execute begin --solo` on such a resume, so t-16 needs to place `execute begin` after §0 step 8's continue/reset question.
- [locked-decision] Carried over: t-10's "silent with neither test_command nor lanes" carve-out is still not recorded in spec.toml.
- [side-effect] t-2's temp-index `git add` writes blob objects into `.git/objects` for every modified or untracked-unignored file, twice per `dross test` (before and after). It is harmless, but loose objects accumulate and large unignored files are re-hashed on every run.
- [spec-level] c-7's reader list lets `grep KEY .env` (no `-q`) print matching lines. t-7's allow table only exercises `grep -q`.

## Summary
The plan is careful, and the amendment fixed the previous blocker's mechanics, but t-19 silently overturns test-lane-config's locked `bare_test_run` and doubles every full run in feastahead; that needs a user decision recorded in the spec before execution, and the pathfence-audit and panic-exit-2 gaps should be closed in the same pass.
