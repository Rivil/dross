## FLAG
- [test-contract / c-4] Two ordinary dross verbs can still disarm the gate or move a dirty diff onto a fresh review record, and t-20 covers neither. Both are simpler than the `rm`/`mv`/`git clean` resets that t-6 now closes, and both are plain direct invocations, which shell_detection_depth counts as in scope.
  - (a) `dross task status <p> <t> pending` or `done` while code is dirty. With no task in_progress, solo-review goes silent; TestSoloReviewSilent in t-18 actually asserts that silence. The commit then passes on commit-green alone. Setting a different task in_progress instead hands the dirty diff to that task's fresh record. t-12 guards only `failed`.
  - (b) `dross quick begin --solo "<anything>"` while a solo execute task is armed with dirty code. t-19 says "solo quick at HEAD wins", so the agent gets an empty quick record and has t-3's diff reviewed against a description it wrote itself. t-20's prose ("a non-solo … `dross quick begin`") is ambiguous, and its table pins only the pair form `dross quick begin "x"`. Path (b) also leaves no trace in changes.json, because t-12 attaches nothing for quicks.
  Suggestion: add TestSoloDowngradeGuard rows (or extend t-12's dirty-tree guard) so that, while armed with code dirty, `dross task status <p> <armed-task> pending|done` and `dross quick begin --solo …` both refuse.
- [test-contract / c-8] A solo quick has no criterion for a spec finding to cite, and t-2 rejects any spec finding without one: its parse table says "a spec finding with no criterion → errors", with no exception for scope. The reviewer body in t-7 and TestReviewerBodyScopesSpecFindings are written for tasks only (covered criteria, description, test_contract). Nothing says what a quick's spec finding cites. So a fixable spec gap in a quick most likely fails to parse. The recorder then marks it unavailable (sticky), and t-17 discards the quick with no fix round. c-8 promises the quick a spec-compliance check, and t-17 promises one fix round.
  Suggestion: decide what a quick-scope spec finding cites, for example a fixed token naming the description. Pin it in t-2's parse table (quick scope accepts it, task scope still rejects an empty criterion) and give t-7's body a quick-scope worked example that ParseVerdict accepts.
- [architecture] t-3 risks an import cycle that would surface at t-6 (wave 2). TestContextMalformedGatesRefuses makes `review.BuildContext` responsible for handling gates.toml and the secret list. But `LoadLists` lives in `internal/gate/lists.go` and `SecretPattern` in `internal/gate/secrets.go`. If t-3 simply imports `internal/gate`, and nothing in t-3 says it must not, then t-6's `rounds []review.Round` in `internal/gatestate` closes the cycle review → gate → gatestate → review. (`gate/pair.go` and `gate/commit.go` already import gatestate.) t-6 would then fail to compile, and fixing it means reworking t-3 after it has been committed. t-10 later adds a second edge, gate → review.
  Suggestion: state in t-3 that `internal/review` never imports `internal/gate`. BuildContext should take the secret patterns, the gates.toml error and a matcher func as parameters. The malformed-gates.toml row then asserts that BuildContext refuses when given that error, and the callers (t-10 via `Call.Lists`, t-13 via `gate.LoadLists`) are pinned by TestContextDigestParity and TestContextVerbDigest.
- [files] t-15 will turn existing doctor tests red, and their file is not in t-15's list. `withConfig()` in `internal/cmd/doctor_hooks_test.go` points CLAUDE_CONFIG_DIR at a fresh temp dir, replacing the one that t-11's `chdir()` seeds with the reviewer. The following tests then assert that doctor exits 0, and once a missing reviewer makes doctor exit non-zero they fail:
  - TestDoctorGateHooks, after `dross hooks ensure`;
  - the missing-convenience-hook table ("a missing convenience hook failed doctor");
  - TestDoctorProjectHooksDisabled, both its baseline and the per-file `err != nil || sec != baseline` checks.
  Suggestion: add `internal/cmd/doctor_hooks_test.go` to t-15's files, and either have `withConfig` seed the reviewer or have those tests install it.
- [files / granularity] t-6's TestReviewRecordDeleteRefused can only pass if `tamperTarget` in `internal/gate/override.go` learns `rm`, `mv` with the record as source, and `git clean`. Today it reads only redirects, `tee`, and the last `cp`/`mv` operand. `override.go` is not in t-6's files. The row also pins only `git clean -fX .dross`, an ancestor path that `isGateRecord` does not match today. Three other commands delete review.json just as effectively and are left unpinned: `rm -rf .dross`, a path-less `git clean -fdX` at the root, and `git stash --all`. t-6 also mixes two packages and two concerns: the new gatestate records, and a change to tamper-guard that affects every gate record in every repo.
  Suggestion: add `internal/gate/override.go` to t-6, decide which ancestor forms are in scope, and pin them. Consider moving the tamper-guard rows into their own task.
- [test-contract] The identity of a quick "attempt" is never defined. t-6 puts an `attempt` field in review.json. t-18 says "a pass from another quick attempt refuses", and t-10 says "a later pass for the same attempt". But t-19 gives a scope key, (phase, task) plus treefp.Base, only for execute scopes. If a quick attempt is keyed on quick.json's `at`, then re-running `dross quick begin --solo` over an armed, dirty solo quick creates a new attempt and clears an exhausted or unavailable record. t-20 does not guard that path.
  Suggestion: define the quick scope key in t-19's description and table. Add a TestSoloDowngradeGuard row for `quick begin --solo` over an armed solo quick with code dirty.
- [c-5 / t-1] t-1's isolation check covers only the project-level CLAUDE.md, because the canary sits in the scratch repo. c-5 also excludes the user's CLAUDE.md and auto-memory, and the plan never shows empirically that either is excluded. There is a second risk. The reviewer is "told to quote every instruction", and its reply is committed as testdata to a public repo (`remote.public = true`). If omitClaudeMd fails to drop the user-level CLAUDE.md, the user's private global instructions end up in the fixture, and nothing in t-1 checks for that before the commit.
  Suggestion: before committing, have t-1 scan the captured reply, read-only, for a few distinctive lines from the real `~/.claude/CLAUDE.md` and a known MEMORY.md entry, and STOP on a match. Pin that check in TestCapturedReviewerIsolation.
- [user preference] t-16 and t-17 require a FOREGROUND reviewer spawn, and TestExecuteReviewerSpawnForeground fails if `run_in_background` is permitted. That reverses the user's standing directive in auto-memory (`dross_agents_background_only.md`): "always pass `run_in_background: true`… applies to… reviewers, any /dross-* fan-out… unless the user explicitly asks". The design reason holds, since t-1's background fixture carries no verdict. But every solo task will now make a blocking spawn, and neither the spec nor the plan records that the user accepted this.
  Suggestion: get the user's explicit OK and record it. A spec decision beside reviewer_isolation would fit, so the foreground rule is not read later as drift.
- [test-contract / quality_blocking] TestReviewerBodyMatchesParser checks only that t-7's reviewer body *names* the three grades. The locked quality_blocking decision defines what BLOCKING covers: a correctness bug, an unmet test_contract, or a violation of a locked decision or rule. A body that names the grades without that definition passes the test, yet leaves the reviewer free to block on style or to grade an unmet test_contract as FLAG.
  Suggestion: pin the four BLOCKING triggers, and a statement that style is never BLOCKING, in TestReviewerBodyMatchesParser.

## NOTE
- [wave-order] t-1 runs in wave 1, before t-2 fixes the verdict schema and before t-13 fixes the context-line format. TestRecorderClaims in t-10 requires "t-1's captured envelope carrying a pass verdict and a matching context line". No capture taken in a wave-1 scratch repo can carry a digest that matches t-10's fixture repo. So t-10 will have to splice its own prompt and verdict into the captured envelope. Only the envelope shape stays a real capture. Saying this in t-10 would stop an implementer from trying to re-capture.
- [c-5] TestRecorderRejectsWidenedPrompt makes "the context line plus any other text" a sticky unavailable, while a prompt with *no* context line is only stale and can be retried. The plan does not say whether surrounding whitespace or a trailing newline counts as "other text". If it does, a formatting slip fails the task permanently with no fix round.
- [scope] In a repo with no `runtime.test_command`, execute.md and quick.md skip the test gate, but solo-review stays armed: t-19 has no equivalent of commit-green's no_test_repo silence. t-16 and t-17 run the review only "after green `dross test`", so solo commits there are refused until the agent follows the gate's remedy. The plan states no intended behaviour for this case.
- [scope] `dross review context` refuses an empty code diff (t-13), and t-16's branch list (pass / blocked / still blocked, unavailable or spawn error) has no path for that refusal. A solo task that turns out to need no code change has no defined way through.
- [test hermeticity] `TestMain` in `internal/cmd/hermetic_env_test.go` pins HOME but not CLAUDE_CONFIG_DIR. The existing TestInstall* tests build `installer{home: tmp}` and call `run()` without `chdir()`. Once t-11 makes `run()` write to and prune `$CLAUDE_CONFIG_DIR/agents`, any host that exports CLAUDE_CONFIG_DIR will have `go test` write into its real agents dir and prune it. The variable is unset on this machine.
- [c-8 / quality_blocking] t-3 renders the phase's locked decisions plus hard rules "(or a quick's description)". So a quick's context includes no rules, and the reviewer has nothing to judge a rule violation against, which is one of quality_blocking's BLOCKING triggers.
- [granularity] t-18 still puts the extraction of commit-green's candidate builder in the same commit as the new gate. Round 1's split was applied to the downgrade guard (now t-20), not to the refactor. The regression net is TestSharedCandidate plus the existing commit_test.go suite; that is acceptable, but this remains the riskiest commit in the phase.
- [strength] Round 1's findings were addressed concretely, not just acknowledged:
  - the c-2 amendment plus TestReviewerBodyScopesSpecFindings settles how a split criterion is judged;
  - t-10 now comes after t-13;
  - t-7 depends on t-1, with the STOP widened;
  - the spawn-error branch is restored in t-16 and t-17;
  - tamper-guard deletion rows were added;
  - a malformed gates.toml now refuses;

  - ordering is pinned by TestQuickDiscardBeforeEnd.
- [strength] t-19 keys the scope on `treefp.Base`, not on HEAD. That closes the reset through a `.dross/`-only or `--allow-empty` commit by construction, not by detecting the command. TestReviewRecordSingleWriter, together with the gate-off-guard row, enforces review_pass_signal structurally.
- [strength] The data model fits the existing code. `changes.Reviews` is kept apart from `Tasks`, so a failed task's files stay out of verify's mutation scope. The changes→review import cycle through `phase/done.go` was anticipated in t-5. The contracts are concrete throughout: config-independent patches, an untouched index sha256, and a 60,000-char cap on the PR body.

## Summary
Nothing blocks: every criterion is covered, no locked decision is contradicted, and round 1's findings were fixed. Before t-2, t-7 and t-20 are executed, two gaps should be settled: the verb-level disarm paths (`task status pending|done`, `quick begin --solo`) and what a quick-scope spec finding cites. Separately, two file lists are missing a file the task must edit (override.go for t-6, doctor_hooks_test.go for t-15), and t-3 needs a no-`internal/gate`-import rule to avoid an import cycle.
