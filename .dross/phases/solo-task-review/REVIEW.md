# Plan Review — solo-task-review

Reviewed: 2026-10-04
Plan: 18 tasks across 5 waves

## BLOCKING
- [test-contract / design] When a criterion is split across tasks, the reviewer will raise blocking spec findings for every part a sibling task owns. t-7's reviewer body copies c-2's rule as written: "a covered criterion's sub-surface with no code or test is a spec finding (always blocks)". t-3's context gives the reviewer only this task's record and the full text of each criterion the task covers. It does not say which sibling tasks own the other sub-surfaces. In this plan every criterion is spread over 3–7 tasks (c-1: t-1/3/10/13/14/16; c-8: seven tasks). Take t-3: its diff (treefp.Patch plus BuildContext) has no code for c-1's "pair mode spawns no reviewer" or "before its commit". The reviewer flags that as a spec finding, and spec findings always block. No fix round inside t-3 can clear it, so t-3 is marked failed and `NextRunnable` blocks its dependents. t-1 claims c-1 on the strength of a fixture capture alone. No contract in t-3 or t-7 says how to judge a sub-surface owned by another task. This phase's own tests would stay green, while real solo runs would fail most tasks of any normally decomposed phase. The plan contradicts no locked decision, but t-3 fixes the context shape (and the digest is computed over it) and t-7 fixes the reviewer body, both in waves 1–2. That makes this a decide-before-execution item.
  Suggestion: settle the scope of "covered" for the reviewer before wave 1. A spec clarification would fit, like the one D5 added for review_input. Either limit each criterion to the slice in the task's description and test_contract, or have the context list the sibling tasks that cover each criterion. Then pin the choice in two places: a TestContextScope row in t-3 (sibling ownership is rendered) and a TestReviewerBodyMatchesParser worked example in t-7 (a sub-surface owned by a sibling task yields no spec finding).

## FLAG

TestRecorderStaleContext requires the recorder's warning to name `dross review context`. `cmd/dross/gate_remedy_test.go` TestGateRemediesResolve scans every non-test string literal in `internal/gate/*.go` for `` `dross <verb> <sub> `` and resolves each one against `newRoot()`. The `review` verb does not exist until t-13, and t-13 depends on t-10. So t-10's full `dross test` goes red and commit-green refuses t-10's commit.
  Suggestion: decide before wave 3. Either register a bare `review context` verb stub in or before t-10, or add a temporary `narratedIgnore` entry in t-10 that t-13 removes. In both cases, add `cmd/dross/main_test.go` or `cmd/dross/main.go` to that task's files.
- [wave-order] t-7 does not depend on t-1, although t-1 is the go/no-go for exactly what t-7 ships. t-1's STOP only reaches "before t-10". If the canary leaks, reviewer_isolation has to be re-decided. That invalidates t-7's `omitClaudeMd` definition and, downstream, t-11, t-14 and t-15. Because waves run in order, wave 2 (t-6..t-9) would be built and committed before the STOP takes effect.
  Suggestion: add t-1 to t-7's depends_on and widen t-1's STOP to "before t-7 and t-10".
- [test-contract] The "reviewer cannot run" branch of review_unavailable was lost when the drafts were merged. review_unavailable requires that a task whose reviewer cannot run is marked failed, naming the cause. PostToolUse fires only after a tool call succeeds. A spawn that errors (unknown agent, API or rate-limit failure, interrupt) therefore records nothing, and `dross review status` reads "none", not "unavailable". t-16 branches only on pass, blocked, and still-blocked-or-unavailable. t-12 derives a reason only from exhausted or unavailable records. The risk draft had "still blocked, unavailable or the spawn errored → stash → failed (--reason only for a spawn error)" (panel/risk.md:321); the merged t-16 dropped the spawn-error part. The gate still fails closed, since with no record the commit is refused. But the task is never marked failed, so the loop has no defined way out.
  Suggestion: put the spawn-errored branch back into t-16's description. Add a TestExecuteReviewFailurePath row: spawn error → stash → `dross task status … failed --reason <cause>`.
- [test-contract] The exhausted and unavailable states can be wiped without any gate refusing. Both live only in `.dross/gate/review.json`. tamper-guard (`internal/gate/override.go` tamperTarget) catches redirects, `tee`, and the *target* of `cp`/`mv`. It does not catch `rm .dross/gate/review.json`, `mv .dross/gate/review.json /tmp/` (the file as source), or `git clean -X`. After a delete the state is none, the gate's remedy says to run `dross review context`, and the agent gets fresh rounds. That defeats c-3's one-fix-round cap and the stickiness of review_unavailable. Until now, deleting any gate record made the gate stricter (no green.json or approval.json means refuse). review.json is the first record whose deletion makes it more lenient. Two more ways to reset:
  - A new HEAD starts a fresh record (TestArmedScope), and a `.dross/`-only or `--allow-empty` commit moves HEAD without any gate check (`onlyDross([])` is true).
  - TestSoloDowngradeGuard lets `dross execute begin p --solo` through while a solo quick is armed with dirty code. Under t-14 that call deletes quick.json, which un-arms the quick.

  Suggestion: either add tamper-table rows to t-6 for `rm` and `mv`-as-source on review.json (extending tamperTarget), or record that these resets are accepted under tool-gate-hooks' shell_detection_depth. Either way, add a TestSoloDowngradeGuard row for `execute begin --solo` over a dirty solo quick.
- [test-contract / c-5] The reviewer can read files that c-5 says it never sees. t-7 gives it Read, Grep and Glob with no path limit. t-3 carefully keeps uncovered criteria, unlocked decisions and other tasks out of the context, but each of these is one Read away: `.dross/phases/<id>/spec.toml`, `plan.toml`, a repo CLAUDE.md, `~/.claude/CLAUDE.md`. The secret-read gate also checks Read calls but not Grep. c-5 says the reviewer "sees only" the listed inputs, yet TestReviewerDefinitionIsolation checks only the frontmatter. A strict verify reading (as D4 anticipated) has nothing to judge against.
  Suggestion: have t-7's body limit reads to repo source files: nothing under `.dross/` except the named context file, no CLAUDE.md, nothing under `~/.claude`. Pin that sentence in TestReviewerBodyMatchesParser or TestReviewerDefinitionIsolation.
- [test-contract] t-17 does not pin the order "discard, then `dross quick end`". t-18's downgrade guard refuses `quick end` while a solo quick is armed with dirty code, so quick.md's blocked-review and solo-red paths must discard first. t-16 pins the same kind of ordering (stash before `failed`). TestQuickSoloReviewBlocked and TestQuickMarkerClosed only check that the steps are present.
  Suggestion: add an ordering clause to TestQuickSoloReviewBlocked and TestQuickMarkerClosed.
- [test-contract] No contract says what happens to secret withholding when gates.toml is malformed. t-3 and t-13 withhold secret paths using the list as extended by gates.toml (TestContextDigestParity includes "a secret path added via gates.toml"). Neither says what `review context` or the recorder does when gates.toml does not parse (`Lists.Err`). In that state LoadLists returns only the defaults. The contents of a user-added secret path would then be written into `.dross/gate/review-context.md` and into the reviewer's transcript. The other Extensible gates refuse in that state.
  Suggestion: add a row to TestContextWithholdsSecretPaths or TestContextVerbRefuses: with a malformed gates.toml, refuse and name the file.
- [test-contract] t-11's last row can't fail when t-11 is committed. It says "the existing TestExecuteBeginRecordsMode and Doctor() tests go red once t-14/t-15 land". At t-11's own commit nothing fails if `chdir()` stops seeding the reviewer.
  Suggestion: replace it with a direct assertion in t-11's tests: after `chdir()`, ReviewerStatus == ok.
- [granularity] Four tasks touch 5 files. t-2, t-4 and t-14 reach five only because of `not_paths.txt` or `cli_tree.txt`, so none of them needs splitting. t-18 is a real split candidate. It does four things in one commit:

  Suggestion: consider splitting t-18 so the candidate-builder extraction (TestSharedCandidate plus commit_test.go) lands separately from the gate and the downgrade guard.

## NOTE
- [architecture] Once t-10 lands, `internal/gate` imports `internal/review`. So t-3's BuildContext cannot call `gate.SecretPattern` or `gate.LoadLists`; it has to receive the matcher or patterns as a parameter. The plan doesn't say this; the compiler will force it.
- [environment] The digest is computed in two different processes. `dross review context` runs in the Bash tool's environment, which is initialised from the user's shell profile. The recorder runs in the hook's environment. `gitrun` passes `os.Environ()` through unchanged. TestPatchConfigIndependent covers git config keys but not environment variables such as GIT_DIFF_OPTS or GIT_CONFIG_PARAMETERS/COUNT. TestContextDigestParity computes both digests in one process. If the two environments diverge, every review will read as "stale".
- [c-5] `omitClaudeMd` needs Claude Code 2.1.271 or later, and older versions ignore the key silently. Neither ReviewerStatus nor doctor checks the Claude Code version, and t-1 proves the key works only on the author's install. Auto-memory exclusion rests only on the structural check that there is no `memory` key: t-1's scratch repo has no auto-memory that could leak.
- [c-6] For a quick record, t-12 attaches nothing to changes.json. Solo-quick verdicts, including FLAGs on a quick that passed, are therefore kept only in the machine-local review.json. That reads c-6 as applying to phase tasks only. Worth confirming.
- [scope] The review context has no size limit. Tasks that add whole files (t-1's captured payloads, regenerated goldens) put the entire file into the context, and an overflow shows up as "unavailable", which fails the task. Separately, `make uninstall` does not remove `~/.claude/agents/dross-*.md`.
- [strength] t-1 is an explicit, empirical go/no-go. It asserts real-capture provenance (session_id, transcript_path, `toolu_` id) and includes a CLAUDE.md canary, following the precedent of the AskUserQuestion fixture. The two platform assumptions nobody has verified yet (that omitClaudeMd works, and that the Agent tool_response carries the final text) get tested before any code depends on them.
- [strength] The fix-round cap and the stickiness of "unavailable" are enforced in code: t-2's ledger table and t-18's fail-closed posture, not left to the prompt. The data model fits the existing code. Reviews go in a separate map because verify.go feeds `ch.Tasks[*].Files` into the mutation scope. `failed` refuses a dirty tree (t-12), and t-16 updates the existing solo red path to stash first.
- [strength] The ordering respects r-01: solo-review is the last task id, so `make install` does not arm it on this repo before execute.md and quick.md teach the loop. The contracts are concrete throughout, for example config independence (color.ui, diff.external, textconv), an untouched index sha256, and the 60,000-char PR body cap.

## Summary
One design gap must be settled before t-3 and t-7 fix the context shape and the reviewer body: as written, any criterion split across tasks will produce false blocking findings. Apart from that the plan is unusually well grounded in the existing code. The issues most likely to bite during execution are the t-10/t-13 naming-before-registration defect and the dropped spawn-error branch.
