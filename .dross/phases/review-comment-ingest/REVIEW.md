# Plan Review — review-comment-ingest

Reviewed: 2026-10-06
Plan: 17 tasks across 7 waves

## BLOCKING
- [locked-decision] `command_surface` (locked) says `dross pr reply` exists "so c-5's confirm gate and posted-tracking are enforced in Go rather than by prompt prose". The plan doesn't deliver the confirm half of that. t-14's draft run prints the `--confirm <digest>` line to the stdout of the agent's own Bash call. Nothing in Go can tell a user-approved `--confirm` from the agent pasting that digest into its next call. So the user confirm still rests entirely on prompt prose: t-15's TestRespondPromptRequirements checks that "every `--confirm` sits after an AskUserQuestion step". That is exactly the mechanism the decision says it replaces. What Go does enforce is narrower: the posted body equals the previewed draft, and posted-tracking. No contract in t-14 shows that a correct digest without a human answer posts nothing.
  Suggestion: pick one before execute. (a) Tie `--confirm` to a recorded AskUserQuestion answer, using the approval-recording pattern `internal/gate/pair.go` already uses: PostToolUse records an exact-label answer, and the verb refuses unless a matching record exists for this digest. Add a t-14 contract: a correct `--confirm` with no recorded approval → 0 POSTs. (b) Amend the decision's `why` to say plainly that Go enforces preview-binding and posted-tracking while the human confirm stays at prompt level, and word t-14's contracts to match.

## FLAG
- [antipatterns/files] t-1 and t-8 both name TestEveryPathShapedFieldIsDeclared in their contracts. Neither lists `internal/cmd/testdata/pathfence_scan/not_paths.txt` or `internal/pathfence/fields.go` in `files`. That walker requires every json/toml-tagged string field under internal/ to be filed. The new GitHub and REST decode structs will carry tagged `body`, `html_url`, `login`, `type`, `path`, `ref`, `full_name`, `state`, `new_path`, `display_name` and so on. Existing rows such as `ship.forgejoPR.HTMLURL` and `ship.PRAuthor.Login` show this is required. The inline `path` field also needs a `pathfence.Fields()` disposition. As written, t-1/t-5 (wave 1) and t-7/t-8 (wave 2) each touch the ledger without saying so.
  Suggestion: add the ledger (and fields.go for the inline `path` field) to t-1's and t-8's `files`.
- [rollback] t-13's route path runs "…then mirrorDeferredAdd. Then Upsert + Save; on Save failure plan.toml/spec.toml are restored byte-for-byte." `mirrorDeferredAdd` pushes a backlog issue to the board, and `[board]` is enabled (youtrack). A byte restore cannot undo that network call. A record-Save failure after a route therefore leaves an orphan board issue tagged `dross/deferred:<id>` for an id that no spec holds. TestPRResolveRollsBackOnRecordFailure only checks spec.toml.
  Suggestion: mirror only after the record Save succeeds, and have the rollback test assert 0 board calls on the failure path.
- [granularity] t-13 touches 5 files and carries 14 contracts. It has three write paths: plan via AddTask, spec via deferred plus board mirror, and the record. On top of that it adds cross-file rollback and the `dross validate` integration of pr-triage.toml. The validate wiring is what `triage_record` means by "schema-checked by `dross validate`". It depends only on t-7, so it could land in wave 3 instead of being buried in the biggest task.
  Suggestion: split the validate.go integration and TestValidateTriageRecord into their own task.
- [criterion-fidelity] c-1 requires "a bot/human flag" on each comment. t-8 pins forgejo, gitea and gitlab to `unknown` for every author (TestRESTPRCommentAuthorFlag), so 3 of the 4 provider families never yield bot or human. The tri-state is honest, but the spec doesn't record it, so /dross-verify can reasonably score c-1 partial.
  Suggestion: record the bot|human|unknown tri-state as a spec decision before execute. Or, where the forge exposes it (e.g. a user-lookup endpoint's bot attribute), resolve it and pin that in t-8.
- [test-contract] t-7's description gives `Save(path, readBytes, rec)`, which has no Refs parameter. Yet TestRecordValidate requires that "Save refuses" ref-dependent problems: "a task absent from Refs", "a deferred id absent from Refs". The executor has to guess whether Save takes Refs or validates structure only. The description also says Save "validates, Redacts". Validating before redaction means the persisted (redacted) form is never the form that was validated.
  Suggestion: settle Save's signature (and the validate/redact order) in the description so the contract and the API agree.
- [security] t-4 says "No author check". Its boundaries drop any text outside a finding: before the first finding, under a heading before the next finding, and after `---`. That text is never rendered or triaged. Any commenter who opens with `## /dross-review` plus one finding bullet gets the rest of their comment excluded from triage. That is the same "third party hides a comment" hole the `self_reply_exclusion` why closes for the reply marker. No contract covers residual text.
  Suggestion: decide how residual non-template text is handled (surface it as its own item, or refuse to split when it exists) and add a t-4 or t-9 contract for it.
- [reply-content] t-11 puts `@author` in every bullet of a comment that gets posted. On GitHub and GitLab that is a mention: it notifies the commenter and wakes review bots that answer mentions. The bot's reply arrives as a new untriaged comment, and a rejected bot gets mentioned again on the next run. Also, only the reason is OneLine'd. The author is third-party controlled (Bitbucket display names), and TestReplyReasonCannotForge covers only the reason.
  Suggestion: decide whether the mention is intended (a plain login in backticks avoids it), OneLine the author, and cover both in t-11.

## NOTE
- [wave-order] t-13 and t-14 are both wave 5 and both edit `internal/cmd/pr.go` and `cmd/dross/testdata/cli_tree.txt`. `dross task next` runs tasks sequentially, so this is safe today, but they are labelled as parallel when they are not.
- [coverage] c-8 is effectively GitHub-only. `ship.ListOpenPRs` refuses every non-github provider and `openPRDigest` returns nil, so REST forges never get ship-PR lines to put counts on. That doesn't conflict with `provider_scope`, which covers fetch and reply, but the plan doesn't say it.
- [test-contract] t-12 makes a failed lookup look identical to "none" (TestWatchUntriagedDegrades). A PR with untriaged comments and a transient fetch error shows no count. This matches openPRDigest's never-fail-the-tick posture, but it is a deliberate gap in c-8's "a PR with none shows no count".
- [coverage] t-17 (the ship refusal while an accepted task is undone) closes a real gap. A `.dross/`-only plan change doesn't trip `gateFreshness`, so without it an accepted comment could ship unexecuted. But no criterion asks for it, and it maps to c-2 only by inference, so /dross-verify needs to map it on purpose.
- [granularity] t-15 trips the 5+ file threshold (7 files). Three of those are audit ledgers that TestInteractionAuditEnumeratesEveryInteractiveCommand, TestSubagentOffloadAuditCoversEveryPrompt and TestFooterCoverageFailClosed force into the same commit, so it is not a real split candidate.
- [locked-decision] `provider_scope` reply parity rests on the existing per-provider `ship.PostComment` tests. t-14 exercises a single stubbed forge. t-14 names `buildCommentOpts`, but t-10's prThread description ("builds OpenOpts from [remote] + remotePolicy hosts") doesn't name the existing `buildOpenOpts`. Reusing it keeps APIBase/AuthEnv/AuthUser/Hosts wiring for REST forges from being reimplemented untested.
- [strength] Each new spawn, decode, writer and field is tied to a named existing ratchet. All 27 referenced guard tests exist in the tree (checked), and none of the ~100 new test names collides with an existing one, so TestNoTestLost stays green.
- [strength] The security contracts are adversarial and name the exact surface that breaks: a CommonMark closer-scan oracle plus a fuzz target for the fence; Bitbucket `next` pointed at a second httptest host that must see 0 requests; `--cmd "touch pwned"` must not run; fail-closed handling of partial pages; self-exclusion that requires both the marker and the author ID.
- [strength] TestSplitReviewMatchesReviewTemplate pins the splitter to the live `review.md` §4 template. That template holds an indented "```snippet```" line, which a naive fence detector would read as an opener, swallowing the second finding. The test catches exactly that drift.

## Summary
The plan is thorough and well guarded, but t-14's `--confirm` digest leaves the user confirm to prompt prose, which contradicts the locked `command_surface` rationale. Resolve that, and fix the incomplete ledger file lists and the board-mirror ordering in t-13's route rollback, before executing.
